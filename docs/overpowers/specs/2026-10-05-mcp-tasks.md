# MCP Tasks integration

## Goal

Move long-running Antigravity observation out of the model turn. A Tasks-aware MCP host receives a durable handle immediately and manages lifecycle requests without waking the controller for each poll.

## Protocol

- Extension: `io.modelcontextprotocol/tasks`, revision `2026-07-28`.
- The server advertises the extension through `server/discover`.
- Only `dispatch_task` creates a Task, and only when the request declares the extension in `io.modelcontextprotocol/clientCapabilities`.
- The Antigravity `job_id` is reused as `taskId`, so completed state survives a bridge restart through the existing NDJSON event store.
- `tasks/get` maps `queued|running` to `working`, `succeeded` to `completed`, `failed` to `failed`, and `canceled` to `cancelled`.
- A completed task embeds the compact default `inspect_task` envelope as the original tool result. It does not include prompt or step diagnostics.
- `tasks/cancel` delegates to the existing cooperative `cancelTask` path.
- `tasks/update` accepts the extension method but has no pending input requests; responses are therefore acknowledged and ignored.

## Compatibility

Tasks are capability-gated. A caller without the extension receives the existing immediate `dispatch_task` response and uses `wait_task` followed by one `inspect_task`. This keeps current Codex and other MCP hosts functional while allowing supporting hosts to avoid model-driven polling.

The core TypeScript SDK v2 does not expose Tasks through its high-level `McpServer` result schema. The bridge therefore uses the SDK's documented advanced low-level `Server` surface and the official `@modelcontextprotocol/ext-tasks` schemas. Ordinary tool calls still pass through the SDK's normal core result validation; only a negotiated task-producing `dispatch_task` bypasses the core-only result codec.

## Token impact

Tasks do not guarantee zero protocol traffic: a host may call `tasks/get` according to the advertised interval, or subscribe to status notifications. The saving is that these lifecycle exchanges are host-managed and compact; they do not create a new model reasoning turn or inject repeated worker events. The terminal response also contains the bounded final inspection, eliminating a separate model-issued `inspect_task` call.
